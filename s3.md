# Section 3 - Configuration System

## 3.1 Overview

The Configuration System is the central mechanic of the game.

Unlike traditional games, where the Settings menu exists separately from gameplay, this project treats the settings menu as a permanent progression tree.

Players gradually unlock gameplay configurations during runs and permanently add them to their available settings.

Most gameplay configurations present a trade-off:

* sacrificing comfort;
* sacrificing visuals;
* sacrificing convenience;

in exchange for gameplay advantages.

This system transforms the traditional "Options" menu into one of the player's primary progression systems.

---

# 3.2 Configuration Categories

Configurations are divided into two categories.

## System Configurations

Always available.

These exist only for usability.

Examples:

* Master Volume
* Music Volume
* SFX Volume

These never affect gameplay.

---

## Gameplay Configurations

Initially locked.

Unlocked permanently by leveling up.

May be enabled or disabled before or during gameplay.

Almost every gameplay configuration modifies difficulty.

---

# 3.3 Unlocking Configurations

Configurations are unlocked exclusively through leveling up.

Whenever the player levels up:

* gameplay pauses;
* three random locked configurations are presented;
* player chooses one;
* chosen configuration becomes permanently available.

Configurations never appear twice.

Once unlocked:

* saved to disk;
* available forever;
* usable in every future run.

---

# 3.4 Activating Configurations

Unlocking a configuration does not automatically activate it.

Instead:

Player opens the Configuration Menu.

Player manually enables or disables unlocked configurations.

This allows different "builds" without requiring multiple save files.

Example:

Run A

* HUD enabled
* 60 FPS
* High graphics

Run B

* HUD disabled
* 15 FPS
* Mouse movement

Same unlocked configurations.

Different active build.

---

# 3.5 Configuration Philosophy

Every gameplay configuration should satisfy at least one of the following principles.

## Reduced Comfort

Example:

Lower FPS.

---

Reduced Visibility.

Example:

HUD disabled.

---

Reduced Ergonomics.

Example:

Mouse-only movement.

---

Reduced Visual Fidelity.

Example:

Low graphics.

---

Increased Enemy Threat.

Example:

Enemies gain ranged attacks.

---

Every sacrifice should reward the player.

The game should never encourage players to disable features without compensation.

---

# 3.6 Configuration Menu

The Configuration Menu remains accessible during gameplay.

Access:

Gear icon.

Location:

Top-right corner.

Opening the menu pauses gameplay.

Closing resumes gameplay immediately.

---

# 3.7 Locked Configurations

Configurations that have not yet been unlocked appear as darkened slots.

Purpose:

* inform players that more configurations exist;
* encourage experimentation;
* communicate progression.

Locked configurations cannot be selected.

---

# 3.8 Configuration Description Window

Every gameplay configuration contains:

Name

Short description.

Gameplay Effect

Exact gameplay changes.

Difficulty Effect

Explanation of how challenge changes.

Flavor Text

Humorous one-liner.

Example:

---

## Low Graphics

Description

Render all entities as simple colored boxes.

Gameplay

Enemy HP reduced by 15%.

Difficulty

Visual readability decreases.

Flavor

> *"Your GPU sent a thank-you letter."*

---

This window is accessible through a "?" button.

---

# 3.9 Configuration Persistence

Gameplay configurations are permanently stored.

Save occurs when the game closes.

Saved information includes:

* unlocked configurations;
* current configuration values;
* currently enabled configurations.

Temporary gameplay progress is never saved.

# 3.11 Balancing Philosophy

Configurations should avoid becoming mandatory.

The strongest configuration is not necessarily the one with the largest numerical bonus.

Instead:

Different players should prefer different combinations.

Examples:

Player A

High graphics.

HUD enabled.

30 FPS.

Mouse movement.

---

Player B

15 FPS.

HUD disabled.

High resolution.

Keyboard movement.

Both should feel viable.

---

# 3.12 Internal Data Structure

Every gameplay configuration should expose the same information.

Example structure:

Configuration ID

Internal unique identifier.

Display Name

Visible name.

Description

Player-facing explanation.

Category

Gameplay/System.

Unlocked

Boolean.

Enabled

Boolean.

Gameplay Effect

Stat modifications.

Difficulty Rating

Estimated challenge increase.

Flavor Text

Displayed in help window.

This standardized structure allows future configurations to be added with minimal code changes.

---

# 3.13 Future Configurations

The system is intentionally extensible.

New gameplay configurations should require minimal implementation effort.

Possible future ideas include:

* VSync
* Camera smoothing
* Screen shake
* Bloom
* Motion blur
* Colorblind filters with gameplay trade-offs
* Dynamic lighting
* Zoom level
* Minimap
* Hit markers
* Damage numbers

Not every future configuration needs to affect gameplay.

However, gameplay-related configurations should continue following the project's core philosophy:

**Less comfort. More power.**

---

# 3.14 Design Goals

The Configuration System should make players:

* experiment;
* laugh;
* optimize;
* intentionally make the game worse;
* discover unusual combinations.

The ideal player reaction is not:

> "I unlocked another menu option."

It is:

> "Wait... if I deliberately play like a complete psychopath, I actually become stronger."

That moment of realization defines the identity of the game.
